# yorkie

[YaneuraOu](https://github.com/yaneurao/YaneuraOu) をベースにした、Rust で書かれた
USI 将棋エンジンです。

> 名称について
> 公開リポジトリ名は `yorkie`、ビルドされるバイナリ名は `yorkie`、USI の
> `id name` は `Yorkie 3.3.0` です。

  8勝6敗で46チーム中16位、2日目のB級リーグは13.6勝4.4敗（13勝1分4敗）で32チーム中2位でした。

  34チーム中13位でした。

## 対応環境

- Linux x86_64 のみ（Ubuntu 26.04 相当を想定）。他の OS は対象外です。
- 評価関数（NNUE）の SIMD カーネルは、ビルド時に選択されます。実行時の CPU 判定は
  行いません。選択の基準はビルドが有効化している CPU 機能で、AVX-512 の F + BW が
  有効なら特徴変換器と要素ごとのカーネルが、さらに VNNI も有効なら層スタックの融合
  カーネルが SIMD 実装になります。いずれも有効でなければスカラ実装です。本リポジトリは
  `-C target-cpu=native` でビルドする（[ビルドと実行](#ビルドと実行)参照）ため、
  実際に選ばれる実装はビルドしたマシンの CPU で決まります。
- どちらの実装が選ばれても、評価値はビット単位で一致します（近似ではなく厳密に同じ
  値を返すことを、SIMD とスカラの等価性テストで検証しています）。
- 生成されたバイナリはビルドしたマシンの CPU 向けです。別の CPU で動作することは
  保証しません（[ビルドと実行](#ビルドと実行)参照）。マシンの NUMA レイアウトと、
  各ワーカーを固定する論理 CPU も同じくビルド時に決まるため、レイアウトの違うマシンで
  起動すると `isready` が違いを報告して対局を始めません（後述の設定一覧のあとの節を参照）。

## ビルドと実行

Rust ツールチェインは [`rust-toolchain.toml`](rust-toolchain.toml) で固定されています
（`rustup` が自動的に該当バージョンを取得します）。

クローンしたディレクトリに移動してから、リリースビルドします。

```bash
cargo build --release
```

- ビルドされる実行ファイルは `target/release/yorkie` です。
- [`.cargo/config.toml`](.cargo/config.toml) が全プロファイルに
  `-C target-cpu=native` を適用します。生成されるバイナリはビルドしたマシンの
  CPU に最適化されるため、実行するマシン上でビルドしてください。
- 同じファイルは `-C llvm-args=-align-all-functions=5` も適用し、すべての関数の
  先頭を 32 バイト境界にそろえます。探索の内容（局面ごとのノード数と指し手）は
  変わらず、AMD EPYC 9B45 で測った 1 スレッドの探索速度は 1.5% ほど上がります。

リリースビルドのバイナリには、DWARF の行テーブル（どの命令がどのソース行から
生まれたかの対応表）が入ります。`perf annotate` や `objdump -dS` が実行中の
命令をソース行に対応づけられるようにするためです。この情報は実行時に読み込まれない
ので対局中のコストはありませんが、そのぶんファイルは大きくなります。配布用や
大会機に置くバイナリでは、ビルドしたあとに取り除けます。

```bash
strip --strip-debug target/release/yorkie
```

消えるのは DWARF セクションだけで、シンボルテーブルは残ります（`perf` は関数名を
解決できます）。実測例（AMD EPYC 9B45 / Zen 5 上の `cargo build --release`）では、
4,715,200 バイトのバイナリが 1,269,952 バイトになりました。

エンジンが受け付けるコマンドと出力する行は、`verbose1` / `verbose2` /
`verbose3` という 3 つの Cargo feature で決まります。`verbose2` は `verbose1` が
持つものを含み、`verbose3` はその両方を含みます。この 3 つをどれも指定しない
ビルドが対局用ビルドなので、`verbose0` という feature はありません。

| ビルド | 読むもの・出すもの |
| --- | --- |
| feature なし | 対局で使うコマンドと、対局で使う出力だけ。探索出力は `bestmove` のみ |
| `verbose1` | ＋受け付けられない入力（認識できないコマンド、不正な `position`、対局では使わない `go` の指定）や定跡ファイルの異常を `info string` で報告する。入力への対処自体はどのビルドでも変わらず、報告するかどうかだけが変わる。あわせて、探索を終える `bestmove` の直前に 1 応答ぶんの統計行を出力し（後述）、`ponder` 設定が有効なビルドでは `bestmove` のあとに始まる探索の開始と終了を `info string ponder start` / `info string ponder stop` で報告する。定跡から指す手では `bestmove` の前に、どちらの定跡から指したかを `info string book: yorkie`（yorkie 定跡）または `info string book: ybb`（`.ybb` 定跡）で知らせる |
| `verbose2` | ＋探索の経過と結果を伝える `info` 行（反復深化ごとの PV、`bestmove` 直前の最終 PV、定跡ヒット時の multipv ブロック）を出力し、対局では使わない `go` の指定（`depth` / `nodes` / `movetime` / `infinite` / `mate` / `rtime`）を受け付ける。候補手順を複数本探す `multi_pv` 設定が効くのもこの feature から（これのないビルドには 2 本目を伝える出力がないため、ルート探索は 1 本だけ）。GUI の検討モードに必要な feature |
| `verbose3` | ＋`bench` を受け付け、1 応答ぶんの統計行に評価値の印（`pathdep` / `declrule` / `movelimit`、後述）を加える |

```bash
cargo build --release -F verbose1
cargo build --release -F verbose2   # 検討用ビルド
cargo build --release -F verbose3   # 解析・計測用ビルド
```

`isready` の初期化フェーズで出る `info string`（評価関数の読み込み失敗、NUMA
レイアウトの不一致、ワーカーが載る CPU の報告、定跡の読み込み報告、置換表の配置報告）は、
起動に失敗したときの唯一の手がかりなので、どのビルドでも必ず出力されます。これらの feature が
変えるのは受け付けるコマンドと出力で、同じ config からビルドできるビルドどうし
なら、探索の挙動もノード数も同一です。設定のうち verbosity feature に依存するのは
`multi_pv` だけで、これは `verbose2` のないビルドでは `1` 以外を指定できません
（そのビルドには 2 本目の候補手順を伝える出力がないため）。

上の 3 つとは別に、既定でオフの Cargo feature が 3 つあります。どれも
`verbose1` / `verbose2` / `verbose3` のどれとも組み合わせられます。

| feature | 効果 |
| --- | --- |
| `tt-entry16` | 置換表のエントリを 10 バイトから 16 バイトに広げ、増えた分をすべてキーに充てる（下位 16 ビットではなく 64 ビットのハッシュ全体を保持するので、局面の同一性判定が厳密になる）。クラスタは 32 バイトのままなので 1 クラスタあたりのエントリ数は 3 から 2 に減る |
| `random` | 評価値に局面ごとのノイズを載せる。既定ビルドは同じ局面をいつでも同じ値で評価するため毎回同じ将棋を指すが、この feature を付けたビルドは対局ごとに指し手が変わる。1 局のあいだは同じ局面が必ず同じ評価値になり、`usinewgame` のたびに変わる |
| `csa` | USI エンジンの `yorkie` に加えて、CSA サーバープロトコルのクライアント `yorkie-csa` をビルドする（[CSA サーバーとの対局](#csa-サーバーとの対局)を参照） |

```bash
cargo build --release -F verbose3,tt-entry16
cargo build --release -F random
```

`tt-entry16` は置換表のヒットの仕方が変わるため、探索の出力が既定ビルドとも参照
実装とも一致しなくなります。

`random` のノイズの振れ幅は config の `random` キー（0〜100、単位は歩=100 の
センチポーン、既定は 0）で決まります。評価値は探索の唯一の評価点で
`eval + noise(局面のハッシュ, 対局ごとの種)` になり、ノイズは
`-random/2` 〜 `+random/2` センチポーンの範囲に収まります。対局ごとの種は
プロセス起動時と `usinewgame` ごとに OS の乱数から引き直され、その対局のあいだは
変わりません。詰み・千日手・入玉の判定値は評価点を通らないため、ノイズは
載りません。`random = 0`（既定）ならノイズは常に 0 で、既定ビルドとまったく
同じ手を指します。この feature を付けずに `random` に 0 以外を書いた場合は、
設定が効かない旨がビルド時の警告として 1 行出ます。

エンジンは標準入力／標準出力を通じて USI プロトコルで通信します。引数なしで起動すると
USI のイベントループに入ります。

```bash
./target/release/yorkie
```

正しくビルドできたかは USI ハンドシェイクで手早く確認できます。

```bash
printf 'usi\nquit\n' | ./target/release/yorkie
```

`id name` / `id author` と最後の `usiok` が出力されれば成功です。どのビルドにも
USI オプションは存在しないため、`option name …` 行は出力されません（後述の
「設定はコンパイル時に埋め込まれる」を参照）。

`main` の最新のコードから生成したクレートドキュメントを
<https://ishidakei.github.io/yorkie/> で公開しています。private な項目も含めて
生成しているため、外部に公開していない型・フィールド・補助関数も読めます。

### 設定はコンパイル時に埋め込まれる

このエンジンは**実行時の設定を一切持ちません**。置換表サイズやスレッド数、定跡や
時間管理のパラメータなど、エンジンが持つ設定はすべて [`configs/`](configs/) の
TOML ファイルに書かれ、ビルド時に定数として埋め込まれます。設定を変えるには
ビルドし直します。

```bash
cargo build --release                                  # configs/default.toml を読む
YORKIE_CONFIG=configs/test.toml cargo build --release  # こちらを読む
```

- [`configs/default.toml`](configs/default.toml) は対局用の config です。`YORKIE_CONFIG` を
  指定しないビルドはこれを読むので、クローンして `cargo build --release` するだけで
  そのまま対局に使えるバイナリができます。対局ごとに決まる値（置換表サイズ・
  スレッド数・定跡・通信遅延など）は、対局が決まった時点でこのファイル、または
  `YORKIE_CONFIG` で選ぶそのコピーに書きます。
- [`configs/test.toml`](configs/test.toml) はテストスイート用の config です。置換表サイズ・
  スレッド数・PV 出力間隔の 3 つだけはテストの都合で選んだ値（小さめの置換表・
  1 スレッド・PV 出力の間引きなし）で、それ以外は `configs/default.toml` と同じ値です
  （理由は各キーのコメントにあります）。テストはこの config を指定して走らせます。

  ```bash
  YORKIE_CONFIG=configs/test.toml cargo nextest run --all-features
  ```

- [`configs/test-limits.toml`](configs/test-limits.toml) は 2 つめのテスト用 config です。
  一部の設定を `configs/test.toml` と別の値にしてあります。設定は 1 ビルドに 1 つの値
  しか持てないため、もう一方の値でのふるまい（探索の上限系・検討モード・複数 PV など）
  を検証するテストはこちらでビルドして走らせます。

  ```bash
  YORKIE_CONFIG=configs/test-limits.toml cargo nextest run -p yorkie-protocol --all-features
  ```

探索の枝刈り・延長・手の並べ替えの係数や、時間配分の係数の値は、config とは別の
**SPSA 設定値ファイル**に書かれ、こちらもビルド時に定数として埋め込まれます。
このファイルはパラメータ 1 つにつき `name = value` を 1 行ずつ並べたものです。
[`configs/spsa/`](configs/spsa/) に 2 つあります。

- [`configs/spsa/yorkie.toml`](configs/spsa/yorkie.toml) は対局に使う値です。
  `configs/default.toml` が指定しているので、普通にビルドすればこの値で探索します。
  チューニングの結果を採り入れるときは、チューニングが書き出した SPSA 設定値ファイルでこのファイルを置き換えます。
- [`configs/spsa/yaneuraou.toml`](configs/spsa/yaneuraou.toml) はやねうら王と同じ値です。
  この値でビルドすると、探索がやねうら王とノード単位で一致します。テスト用の
  config（`configs/test.toml` と `configs/test-limits.toml`）はこちらを指定しているので、
  やねうら王との一致を確かめるテストは、対局用の値を変えても影響を受けません。

現時点では 2 つのファイルの値は同じです。

どちらのファイルを読むかは config の `spsa_config` キーで決まります。環境変数
`YORKIE_SPSA_CONFIG` を指定すると、キーより優先してそのファイルを読みます。相対パスは
リポジトリのルートを基準に解決します。変数やファイルが変わると、探索のクレートは
ビルドし直されます。

```bash
YORKIE_SPSA_CONFIG=configs/spsa/yaneuraou.toml cargo build --release  # やねうら王の値で対局用にビルド
```

SPSA 設定値ファイルも厳密に検証されます。登録されたパラメータの抜けや重複、未知の名前、
整数でない値、探索が許す範囲を外れた値はいずれもビルドエラーになり、エラーには
ファイルとパラメータの名前が出ます。

パラメータの値はどのビルドでも定数としてコンパイルされます。実行時に値を読む
経路はないので、別の値で探索させるには、その値を書いた SPSA 設定値ファイルを
`YORKIE_SPSA_CONFIG` で指定してビルドし直します。

feature を 1 つも指定しない既定ビルド（対局用バイナリそのもの）でしか走らないテスト
もあります。対局では使わない `go` の指定を受け取っても探索を開始しないことと、
探索中に `info` 行を 1 行も出さないことを確かめるテストで、feature 指定なしで
走らせます。

```bash
YORKIE_CONFIG=configs/test.toml cargo nextest run -p yorkie-protocol
```

TOML はフラットな `key = value` の並びで、キーの集合・型・範囲がすべてビルド時に
検証されます。キーの過不足、型違い、範囲外の値、読めないファイルはいずれも
**ビルドエラー**になります。既定値へのフォールバックはありません。

その結果、どのビルドでも次のようになります。

- `usi` への応答に `option name …` 行が出ません。
- `setoption` は USI が求める最小限の扱いになります。行は読み捨てられ、出力も
  状態変化も一切ありません（USI は `setoption` への応答を求めていません）。
- `engine_options.txt` / `<eval_dir>/eval_options.txt` /
  `engine_option_profile.txt` は読まれません。

`verbose1` / `verbose2` / `verbose3` が受け持つのは受け付けるコマンドと出力する
行だけで、設定の出所には一切関わりません。実行時に値を受け取る唯一の経路は
`bench` のスレッド数引数で、これはその計測にだけ効きます（`bench` の第 1 引数
`ttSizeMB` は形式だけ検査して捨てます。置換表は下記のとおりビルド時に大きさが
決まる `static` で、コマンドでは変えられません）。

### どちらの NNUE 実装が選ばれたかを確認する

評価関数の SIMD 実装はビルド時に固定される（[対応環境](#対応環境)参照）ので、選択結果は
できあがったバイナリを逆アセンブルすれば確認できます。VNNI の内積命令 `vpdpbusd` の
出現数を数えます。

```bash
objdump -d target/release/yorkie | grep -c vpdpbusd
```

- 0 以外なら AVX-512（F + BW、VNNI）実装が選ばれています。
- 0 ならスカラ実装です。選ばれなかった側のカーネルは、どこからも呼ばれないため
  リリースビルドのデッドコード除去で実行ファイルから取り除かれます。

実測例（AMD EPYC 9B45 / Zen 5 上の `cargo build --release`）では、既定の
`-C target-cpu=native` ビルドで 29、`target-cpu` を AVX-512 を持たない
`x86-64-v2` に上書きしたビルドで 0 でした。

なお `vpdpbusd` は VNNI 実装の有無を示す命令です。F + BW だけが有効で VNNI がない
CPU 向けのビルドでは、特徴変換器などが SIMD 実装でも計数は 0 になります。その場合は
ZMM レジスタの使用有無で判別できます。

```bash
objdump -d target/release/yorkie | grep -c '%zmm'
```

上の 2 つのビルドではそれぞれ 2382 と 0 でした。

## 評価ファイル（`nn.bin`）

本エンジンが読み込める評価関数は、SFNNwoP1536（SFNN-1536） ネットワーク構成の
ものだけです。この形式の `nn.bin` を用意する必要があります。入手先については
本 README では言及しません。

### ビルド時の変換

エンジンは `nn.bin` を実行時に読みません。ビルド時に一度だけ読み、SIMD カーネルが
そのまま読める並び（各配列を 64 バイト境界に整列させ、カーネルが使う順に並べたもの）
へ変換して、`nn.kernel.bin` というファイルに書き出します。実行時に行うのは、この
ファイルを開いて所定のメモリに載せることだけです。デコードも並べ替えもヒープ確保も
起きません。

- 変換元は configs の `original_eval_dir` キーが指すディレクトリの `nn.bin` です。
  相対パスはリポジトリのルート基準で解決されます。
- 変換先は configs の `eval_dir` キーが指すディレクトリです。相対パスは
  **エンジンの実行ファイルが置かれているディレクトリ**基準で解決されます（ビルドは
  そこへ書き、エンジンはそこから読みます）。実行ファイルを別の場所へコピーする場合は、
  この `eval_dir` ディレクトリも一緒にコピーしてください。
- すでにある `nn.kernel.bin` が同じ変換元・同じ並びのバージョン・同じターゲット機能から
  作られたものであれば、変換はやり直しません。異なる場合は書き直します。
- 変換元の `nn.bin` が無い場合でもビルドは通ります。この場合 `nn.kernel.bin` は
  作られず、エンジンは `isready` で読み込み失敗を報告します。

`nn.kernel.bin` の先頭にはヘッダがあり、並びのバージョン、ビルドが対象とした
`target_feature` の集合、ネットワークの各次元、変換元 `nn.bin` の SHA-256、
そして変換時の警告が記録されています。エンジンはこのヘッダを自分がビルドされた
ときの値と突き合わせます。

### ヘッダ検証

変換時（ビルド時）に行う `nn.bin` の検証は次のとおりです。

- バージョンワードが一致しない場合はハード失敗（変換中止＝ビルド失敗）です。別の
  シリアライズ形式のファイルとみなされます。
- ファイル全体のハッシュおよび各セクション（特徴変換器・各レイヤースタック）
  のハッシュが一致しない場合は、警告として `nn.kernel.bin` のヘッダに記録し、変換は
  続行します。エンジンは `isready` でその警告を `info string` として出力します。
- アーキテクチャ文字列は読み取られますが、比較には使われません。

### 読み込みのタイミングと置き場所

- 読み込みは `isready` の時点で行われます。成功すると `readyok` を返します。ファイルが
  無い場合、あるいはヘッダがこのビルドのものと違う場合は
  `info string eval load failed: …` を出力し、`readyok` は返しません。
- パラメータの置き場所は、どのビルドでもバイナリが宣言する `static` 領域です（2 MiB
  境界、リンカが決めたアドレス）。したがってパラメータのアドレスはプロセスの起動から
  終了まで変わらず、評価はそのアドレス＋定数オフセットで各配列を参照します。領域をどう
  埋めるかだけが、ビルドしたマシンの NUMA ノード数で決まります。
  1 ノードなら、ファイルを読み取り専用でその領域の上に共有マッピングします
  （`MAP_FIXED | MAP_SHARED`。そのうえで huge page を要求します）。ページはページ
  キャッシュのものなので、同じホスト上の複数のエンジンプロセスが同じ実体を共有
  します。複数ノードなら、ワーカーが実際に載るシステム NUMA ノードごとに領域を 1 つ
  使い、各領域にノードを束縛して huge page を要求したうえでパラメータを読み込みます
  （最初のページタッチがそのノードで起きるようにするためです）。各ワーカーは自ノード
  の複製を読みます。
- どちらの場合も、その結果は初期化フェーズの `info string` として
  `evaluation network: … MiB; …` の形で報告されます。

### オプション上書きファイルは読みません

参照実装が `isready` で読む `engine_options.txt`（カレントディレクトリ）と
`<eval_dir>/eval_options.txt` は、本エンジンではどのビルドでも開きません。設定の
出所は `configs/` の TOML だけです。評価ファイルが推奨する `FV_SCALE` は
`configs/*.toml` の `fv_scale` に書き、ビルドし直して適用します。

| `minimum_thinking_time` | 整数 | 1〜100000 | 最小思考時間 [ms] |
| `slow_mover` | 整数 | 1〜1000 | 思考時間の倍率 [%] |
| `round_up_to_full_second` | 真偽値 | `true` / `false` | 秒単位に切り上げて時間を使う（秒読み用） |
| `spsa_config` | 文字列 | 任意 | 探索と時間配分のパラメータの値を読む SPSA 設定値ファイル。相対パスはリポジトリのルート基準。環境変数 `YORKIE_SPSA_CONFIG` を指定すると、そちらが優先される。ビルド時にのみ読まれる |

### ワーカーの載る CPU と NUMA レイアウトはビルド時に決まる

ワーカースレッドは 1 つにつき論理 CPU 1 つに固定され、どの CPU に固定するかは
**バイナリをビルドしたときに決まります**。マシンのノード数と各ノードの CPU 一覧も
同じく**ビルドしたマシンの sysfs から読み取って定数として埋め込まれます**。起動後に
エンジンが `/sys` を読むのは、後述の `isready` の比較のための 1 回だけで、どこに
載るかを決め直すことはどの時点でもありません。したがって、次のようになります。

- ビルドには sysfs のある Linux ホストが必要です。読めない場合はビルドエラーに
  なり、「1 ノードとみなす」といったフォールバックはしません。NUMA ハードウェア
  のないホストでも `node0` は見えるので、1 ノードとして問題なくビルドできます。
  読み取るのはマシン全体のレイアウト、つまりオンラインのすべての CPU であり、
  ビルドするプロセスの CPU アフィニティは関係しません。`taskset` の下や、CPU の
  一部にビルドを制限した cgroup の中でビルドしても、埋め込まれるのはマシン全体の
  レイアウトです。問題になるのは実行時のエンジンプロセスにかかる制限で、後述の
  `isready` の比較がそれを見ます。
- `cpu_assignment = "auto"` のとき、どの CPU を取るかは `cpu_ledger` が指す
  台帳ファイルとの突き合わせで決まります。台帳は「どのビルドがどの CPU を取ったか」
  を 1 ビルド 1 行で記録するテキストファイルで、同じマシンで複数のバイナリを
  ビルドしても互いに別の CPU が割り当てられます。ビルドを識別するのは出力先ディレクトリ、
  読んだ config、バージョンの 3 つで、同じビルドをビルドし直したときは既存の行がそのまま
  使われるため取り分は増えません。空き CPU が `threads` に足りなければ、台帳の名前と
  不足数を挙げてビルドが失敗します。台帳を消せば割り当てはやり直しになります。
  `"auto"` は台帳を必要とするので、`cpu_ledger` が空文字列のままだとビルドエラーに
  なります。
- `cpu_assignment` に明示リストを書いたビルドは、台帳をいっさい読まず、台帳に行も
  足しません。取る CPU はそこに書いた CPU そのもので、条件として確かめるのは
  ちょうど `threads` 個か、すべてオンラインか、重複がないかの 3 点だけです。
  同じマシン上の他のビルドと CPU が重ならないようにするのは、そのリストを書いた側の
  責任になります。台帳を使わない config は `cpu_ledger` を空文字列にします。
- `cpu_assignment = "none"` のビルドはどのワーカーも CPU に固定しません。台帳を
  読み書きせず、置換表や評価関数のメモリを特定の NUMA ノードに寄せることもしません。
  `isready` もプロセスの CPU アフィニティを確かめません。ワーカーは起動した側が
  許す CPU の上で動きます。固定するビルドでは、同じバイナリのプロセスはどれも同じ
  CPU に載るため、1 台で同時に 1 つしか動かせません。`"none"` のビルドなら、起動する
  側が `taskset` で 1 プロセスに 1 CPU ずつ与えて、同じバイナリを何本も並べて動かせます。
  自己対局で計測するための設定で、[`configs/tune.toml`](configs/tune.toml) がこれを
  使います。固定するかどうかで変わるのは探索が動く場所だけで、探索の中身は変わりません。
- `threads` がビルドするマシンのオンライン論理 CPU 数を超えているとビルドエラーに
  なります。ワーカー 1 つに CPU 1 つを与えられないためです。
- `numa_nodes` に整数を書くと、ビルド時に得た NUMA ノード数がその数と一致
  しない限り、ビルドが失敗します。対局に使う config がその数を持っていれば、別の
  マシンでその config を使ってビルドしようとしても失敗するので、レイアウトの違う
  マシンでビルドしたバイナリが気づかれずに対局に持ち込まれることはありません。
- `isready` は実行するマシンの NUMA レイアウトを sysfs から読み直し、ビルド時に
  埋め込んだレイアウトと比べます。ノード数が違うか、どれかのノードの CPU 一覧が
  違うか、ワーカーの載る CPU が埋め込んだのと別のノードに属していれば、その違いを
  1 行の `info string` で報告し、`readyok` を返さずに終了します。ビルドしたマシンと
  別のマシンでバイナリを起動した場合が、これに当たります。
  この行は、verbosity feature を付けない対局用ビルドを含め、どのビルドでも
  出力されます。`isready` の初期化フェーズの `info string` は起動に失敗したときの
  唯一の手がかりなので、どの feature もこれを止めません（[ビルドと実行](#ビルドと実行)参照）。
- 同じマシンでも、`taskset` や cgroup の cpuset でプロセスを CPU の一部に制限
  して起動すると、ワーカーの載る CPU のどれかにプロセスが乗れない場合に限り、同じく
  `isready` が報告して終了します。報告する行は足りない CPU を挙げます。ワーカーを
  CPU に載せるために、起動する側が `taskset` や cpuset を用意する必要はありません。
  エンジンは自分でワーカーを固定します。外からかけた制限もワーカーの載る CPU を
  すべて含んでいれば受け付けます。台帳が示す CPU だけを許す cpuset の下で起動するのが、
  これに当たります。
- `isready` は自分が載る CPU を `info string workers on CPUs …` の形で報告します。
  1 台のマシンで複数のエンジンを動かすとき、どのプロセスがどの CPU を持っているかを
  エンジン自身の出力から確かめられます。`cpu_assignment = "none"` のビルドは代わりに
  `info string workers unpinned` を出します。
- 生成されたバイナリの割り当てとレイアウトがビルドしたマシン向けであるのは、その CPU の
  命令セットがビルドしたマシン向けであるのと同じです（`-C target-cpu=native`。
  [ビルドと実行](#ビルドと実行)参照）。別のマシンで、あるいは別の CPU で
  動かしたければ、そのマシンでビルドし直します。

### 対応コマンド

| コマンド | 説明 |
| --- | --- |
| `usi` | エンジン情報を出力し `usiok` を返す。オプション一覧は出力しない（どのビルドでも実行時の設定を持たないため） |
| `isready` | 定跡と評価関数を読み込み、成功すれば `readyok` を返す |
| `setoption name <名前> value <値>` | どのビルドでも行を読み捨てるだけで、出力も状態変化もない（設定できるオプションが存在しないため。USI は応答を求めていない） |
| `usinewgame` | 新規対局の開始（出力なし） |

| `go [btime <ms>] [wtime <ms>] [binc <ms>] [winc <ms>] [byoyomi <ms>]` | 探索を開始し `bestmove <指し手>` を返す。この行は指し手 1 つだけで、どのビルドでもそのあとに何も続かない。対局で使う持ち時間系の指定はすべて既定ビルドで有効。持ち時間を伴う `go`（＝対局の 1 手）に答えたあとの挙動は `ponder` 設定で決まる（上の設定一覧を参照）。`ponder` トークンが付いていた場合は、選ぶものが何もないため読み捨て、残りの行は通常どおり処理する |

| `gameover` | 対局終了 |
| `quit` | 終了する |
| `bench [ttSizeMB] [threads] [limit] [default\|current\|<fenFile>] [limitType]` | 固定条件での NPS 計測。引数はすべて省略可で、左から順に既定値（`ttSizeMB=1024`, `threads=1`, `limit=15000`, ソース `default`, `limitType=movetime`）で埋められる。`ttSizeMB` は整数かどうかだけを検査して捨てる（置換表の大きさはビルド時に決まっており、計測はそのバイナリの置換表で走る）。引数の位置は固定なので、この引数自体は残る。`verbose3` のビルドでのみ有効 |

認識できないコマンドを受け取った場合は読み飛ばします。`verbose3` のない
ビルドでは `bench` はコマンドとして存在しないため、この経路で読み飛ばされます。
`verbose2` のあるビルドでのみ受け付ける `go` の指定を受け取った場合は、指定の
一部だけを適用すると探索の条件が知らないうちに変わってしまうため、その `go`
コマンドを丸ごと実行せず、探索を開始しません。

これらの状況で何が起きたかを出力するのは `verbose1` のあるビルドだけです
（`info string unknown command: <入力行>` や `info string go error: …` の
通知行）。feature なしのビルドは同じ状況でも何も出力しませんが、入力への
対処自体はどのビルドでも同じです。`bench` の集計行はコマンドの
応答そのものなので、`verbose3` のビルドでは必ず出力されます。

コマンドライン用のサブコマンドとして、perft（指し手生成の数え上げ）も利用できます
（[`crates/yorkie/src/main.rs`](crates/yorkie/src/main.rs)）。

```bash
yorkie perft startpos <depth>
yorkie perft sfen <SFEN> <depth>
yorkie perft sfen <SFEN> moves <m1> [<m2> …] <depth>
```

### 1 応答ぶんの統計行

このエンジンは、対局中はヒープを一切確保しない（必要なものはすべて初期化時に
確保して使い回す）ことを設計上の目標にしています。そこまであとどれだけ残っている
かを 1 手ごとに見るために、`verbose1` 以上のビルドは探索を終える
`bestmove`（`bestmove resign` と `bestmove win` を含む）の直前に統計行を 1 行
出力します。

```
info string stats alloc=40321 nodes=1834762 tt_update=1290311 eval_dup=4127 evals=1046215 eval_tt_hits=388904
bestmove 7g7f
```

固定の接頭辞 `info string stats` のあとに `key=value` の項目を半角空白区切りで
並べた行です。値が 0 の項目は書かれず、項目が 1 つも残らない場合は行そのものを
出力しません。`verbose1` のビルドの項目は次の 6 つで、この順に並びます。どれも
前回の応答からこの応答までの区間を数えたものです。

| 項目 | 数えるもの |
|---|---|
| `alloc` | プロセスがヒープから受け取った確保の回数（`position` の解析、`go` の準備、全スレッドの探索、`bestmove` の文字列の組み立てを含む） |
| `nodes` | 探索したノード数。探索の `info` 行が `nodes` として報告するものと同じ量を、全スレッドについて合計したもの |
| `tt_update` | 置換表への書き込みのうち、置き換え条件が成り立ってエントリの中身を書いたもの。深さを問わず、別の局面や空のエントリへの書き込みも含む。指し手だけを書き換えて中身の書き込みを見送ったものは含まない |
| `eval_dup` | 置換表を引いて外れたあと、計算した静的評価値だけを `DEPTH_UNSEARCHED` で書き込むもの（`search` の `Bound::None` の書き込みと、静的評価値だけで beta を超えたときに `qsearch` が `Bound::Lower` で行う書き込み）のうち、書き込む直前に読んだ時点で、そのエントリがすでに同じ局面の静的評価値（`VALUE_NONE` でないもの）を持っていたもの。その後に中身を置き換えたかどうかは問わない |
| `evals` | `search` と `qsearch` がノードの静的評価値を計算した回数。置換表を引いて外れたとき、当たったエントリが静的評価値を持っていなかったとき、PV ノード（エントリが持っていても計算し直す）で数える |
| `eval_tt_hits` | `search` と `qsearch` で、置換表を引いて当たったエントリの静的評価値を、計算せずにそのまま使ったノードの数（PV ノードでないもの） |

`evals` と `eval_tt_hits` を足すと、静的評価値を求めたノードの数になります。
例外は singular extension の検証探索で、このノードは元のノードが求めた静的評価値を
そのまま使うため、どちらにも数えません。王手がかかっているノードは静的評価値を
求めないので、これもどちらにも数えません。`eval_dup` は `evals`（実際に計算した
回数）と比べて読むための数です。

この区間は `readyok` の直後と `usinewgame` の最後にも始まり直すので、起動時の
確保と対局開始の準備は最初の指し手には計上されません。`ponder` 設定が有効な
ビルドが自分の `bestmove` のあとに相手の手番の局面を探索した分は、その応答の
あとに行われるので、次の応答の行に計上されます。探索しなかった応答（定跡の手、
入玉宣言、指せる手がない局面、評価関数を読み込む前の `go`）では、この探索に
よる先読みが区間内になければ `nodes` / `tt_update` / `eval_dup` / `evals` /
`eval_tt_hits` は 0 なので書かれません。

数えることで探索の判断が変わることはありません。各スレッドは自分の持つ整数に
数え、全スレッドが共有する置換表は、中身を書いたかどうかを書き込んだスレッドの
数に返すだけで、表の側では何も数えません。各スレッドの数は探索の終わりに 1 度
だけ区間の合計に足されるので、ノードごと・書き込みごとにスレッド間で共有される
ものはなく、ヒープの確保もありません。対局用ビルドにはこれらの数も、そのための
フィールドも分岐もありません。

`verbose2` / `verbose3` のビルドでは `info` 行を組み立てて書き出すこと自体の
確保も同じ数に含まれます。対局用ビルドに最も近い値を見たい場合は `verbose1`
だけを付けたビルドで測ってください。

#### 応答が拠っている評価値の印（`verbose3`）

`verbose3` のビルドでは、この行に項目が 3 つ加わります。実際に指す手の評価値、
すなわちその手について探索が最後に確定した評価値が、どの規則を経由して
求められたかを表す印です。

```
info string stats alloc=40321 nodes=1834762 tt_update=1290311 eval_dup=4127 evals=1046215 eval_tt_hits=388904 pathdep=1 declrule=1 movelimit=1
bestmove 7g7f ponder 3c3d
```

| 項目 | 1 になる条件 |
|---|---|
| `pathdep=1` | 探索が辿った経路上の千日手判定（通常の千日手のほか、連続王手の千日手、優等・劣等局面の判定を含む）を経由して求めた評価値である |
| `declrule=1` | 入玉宣言勝ちの判定を経由して求めた評価値である。どの宣言規則が有効かはビルド時に決まる定数（`entering_king_rule`）なので、印は 1 つで足りる |
| `movelimit=1` | 手数による引き分け（`max_moves_to_draw`）を経由して求めた評価値である。探索の深さの上限（`MAX_PLY`）はこの印を立てない |

他の項目と同じ規則に従い、値が 1 のときだけ書かれるので、3 つのどれにも当たらない
応答の行は `verbose1` のビルドと同じ数の項目だけの行になります。`bestmove win` は入玉宣言の結果そのものなので
`declrule=1` を伴い、評価値による `bestmove resign` は他の応答と同様に選ばれた
指し手の印を報告します。定跡から指した場合は探索していないため、どの印も付きません。

置換表のエントリを読み出すコマンドはないため、印を知る手段はこの統計行です。
応答のあとでは根のエントリが別の局面のものに置き換わっていることもありますが、
統計行は実際に指した手の評価値の印を伝えます。なお、この印を読んで探索の判断が
変わることはありません。
`verbose3` のビルドも印を持たないビルドとまったく同じ木を探索します。

#### `bench` 1 回ぶんの統計行（`verbose3`）

`bench` の各局面も `bestmove` で終わるので、局面ごとにその直前に統計行が出力
されます。そのうえで `bench` は集計行 `bench: positions=…` のあとに、同じ形式の
統計行をもう 1 行出力します。この行は探索の 5 項目を、実行した全局面について
合計したもので、`alloc` と印の項目は含みません。`nodes` は集計行の `nodes=` と
一致します。

```
info string bench: positions=4 nodes=4183920 time_ms=4012 nps=1042851
info string stats nodes=4183920 tt_update=2791044 eval_dup=10233 evals=2397140 eval_tt_hits=880312
```

合計は `bench` の開始時に 0 から始まるため、それ以前の探索は含みません。
スレッド数を変えた計測で、`go` を使わずに 1 回の実行全体の数を読むための行です。

## CSA サーバーとの対局

Cargo feature `csa` を付けてビルドすると、USI エンジンの `yorkie` に加えて、
CSA サーバープロトコル（バージョン 1.2.1）のクライアント `yorkie-csa` が
できます。`yorkie-csa` は対局サーバーに TCP で接続してログインし、サーバーが
提示した対局を指し、終わると次の対局を待ちます。USI のコマンドは読みません。feature なしの
ビルドにはこのクライアントが含まれず、`yorkie` はどのビルドでも USI エンジンの
ままです。

```bash
cargo build --release -p yorkie -F csa
# target/release/yorkie-csa ができる
```

### 接続先の設定

接続先とログイン情報はビルド時の設定には含めず、起動時に次の環境変数から
読みます。引数は取りません。必須の変数が 1 つでも設定されていなければ、その
変数名を示すエラーで終了します。

| 変数 | 内容 |
|---|---|
| `YORKIE_CSA_HOST` | サーバーのホスト名またはアドレス |
| `YORKIE_CSA_PORT` | ポート番号 |
| `YORKIE_CSA_ID` | ログイン名 |
| `YORKIE_CSA_PASSWORD` | パスワード |
| `YORKIE_CSA_LOG` | 省略可。ログを追記するファイル。省略すると標準エラー出力に書く |

パスワードはどの出力にもログにも書きません。読み込んだ時点でプロセスの環境
変数から消し、`LOGIN` を送ったあとはメモリ上の値も上書きします。ただし、OS が
プロセスの起動時に渡した環境変数の領域（同じユーザーなら `/proc/<pid>/environ`
で読めるもの）までは消せないため、変数を書いた環境ファイルは権限で保護して
ください。ホスト名とポート番号もログには書きません。

### 動作

- 起動するとまず評価関数、置換表、定跡を読み込み、それが終わってから接続して
  ログインします（標準形式の `LOGIN <名前> <パスワード>`）。対局が提示された
  時点で、すぐに指せる状態になっています。
- 対局条件（`Game_Summary`）を読んで `AGREE` を返します。持ち時間は
  `Time_Unit`、`Total_Time`、`Byoyomi`、`Increment`、`Least_Time_Per_Move` と、
  先手と後手に別々の持ち時間を与える `BEGIN Time+` / `BEGIN Time-` を読みます。
  知らないキーや節は読み飛ばします。局面の節に指し手が並んでいる対局（途中局面
  からの対局）にも対応しています。読めない対局条件には `REJECT` を返します。
- 残り時間はサーバーの数字に従います。指し手ごとに付く `,T<消費時間>` を
  （自分の手のエコーでも）使い、加算時間（`Increment`）を足してから消費時間を
  引き、0 を下回らせない、という `shogi-server` と同じ計算で両者の残り時間を
  更新します。探索には USI の `go btime … wtime … binc … winc … byoyomi …` と
  同じ制限を渡します。相手の手を受信した時点から、自分の持ち時間として数えます。
- 相手の手が手元の局面では指せない手だった場合は、ログに記録してその対局では
  探索をやめ、勝敗はサーバーの判定に従います。
- `ponder` 設定は USI のときと同じように働きます。自分の手を送ったあとの探索は、
  相手の手が届いた時点で止まります。
- 指せる手がない場合や、探索が投了を選んだ場合は `%TORYO` を送ります。
- 対局の終了（`#WIN` / `#LOSE` / `#DRAW` / `#CENSORED` / `#CHUDAN`。その前に
  `#RESIGN` や `#TIME_UP` などの理由の行が届く）を受け取ると探索を止め、次の
  対局を待ちます。`REJECT` で取り消された対局のあとも同じです。
- 何も送らない時間が 40 秒続くと、空行を 1 行送ります（キープアライブ。
  プロトコルは 30 秒より短い間隔で送ることを禁じています）。1 行は必ず 1 回の
  書き込みで送るため、空行が指し手の途中に入ることはありません。
- 接続は TLS を使わない TCP で、`TCP_NODELAY` を設定します。サーバーには
  プロトコルの行だけを送ります。
- `SIGTERM` を受け取ったとき、対局していなければ `LOGOUT` を送って終了します。
  対局中（`AGREE` を返して開始を待っているあいだを含む）は、その対局を最後まで
  指してからログアウトします。
- ログには、受信した行（`<`）、送信した行（`>`）、クライアント自身の記録（`#`）を
  1 行ずつ、UTC でミリ秒までの時刻を付けて書きます。開始時と各手のあとには
  `clock +<先手の残り> -<後手の残り>` を（サーバーの時間単位で）書くので、対局を
  あとから再現できます。エンジンの `info string` もここに書き、どこまで書くかは
  USI のときと同じく verbosity feature で決まります。

### 対応していないもの

- 入玉宣言の規則を対局条件の `Declaration` と照らし合わせること。探索が宣言勝ちを
  返した場合は `%KACHI` を送ります。
- 最大手数（`Max_Moves`）による終局を探索に考慮させること。値は読んでログに
  書くだけです。
- 接続が切れたあとの再ログイン。
- TLS と、指し手のあとに評価値や読み筋をコメントとして付ける floodgate の拡張。

## 実装上の特記事項

- 定跡は `.ybb`（バイナリ定跡）形式のみ読み込みます。`book_file` キーが受け付ける
  値も、実際に読み込める `.ybb` の名前だけです。
- 探索の中では、直近 16 手以内に同じ局面が 2 度目に現れた時点で千日手とみなし、
  対局で 4 度目に現れたときと同じ評価（引き分け、連続王手をかけた側の負け、
  盤面が同じで持ち駒だけが増えた側の勝ち）を付けます。YaneuraOu の
  トーナメント用ビルドと同じ判定で、設定では変えられません。変わるのは探索の
  中の判定だけで、サーバーとの対局で千日手が成立するのは 4 度目に現れたとき
  だけです。
- ただし探索を始める局面から 1 手指した局面では、盤面が探索より前に対局で現れた局面と同じで
  手番側の持ち駒だけが減っていても、手番側の負けとはみなさず、さらに前の局面との照合を
  続けます。YaneuraOu はこの場合も手番側の負けとするので、その 1 手には持ち駒の比較だけで
  詰み以外では最大の評価値が付き、探索はその手を読まずに選んでしまいます。探索を始める局面から
  2 手以上指した局面での判定と、引き分けや連続王手の判定は、どの深さでも YaneuraOu と同じです。
